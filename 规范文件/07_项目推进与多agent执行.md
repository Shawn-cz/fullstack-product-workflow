# 项目推进与多 agent 执行

版本：1.3.0｜适用：多任务、多依赖、需要多轮交付或需要启用独立交叉审计子 agent 的软件项目。简单修改只保留目标、动作和验证，不强制建立完整计划。

本文件说明怎样选择下一项工作、控制范围和完成集成。强制动作的唯一编号见规则库 STD-FLOW-01 至 STD-FLOW-08；具体记录复用 T03、T08、T10，不新建另一套项目台账。每位成员仍贯通全栈工作，子 agent 是执行工具，不是团队专业岗位。

## 1. 先确定本轮结果，再拆任务

| 层级 | 回答的问题 | 合格写法 | 不合格写法 |
|---|---|---|---|
| 产品目标 | 谁要解决什么问题，怎样知道有效？ | 指定用户能完成关键任务，说明观察方法 | 做一个先进平台 |
| MVP（确需验证新产品假设时） | 用什么最小可用范围验证最重要假设？ | 目标用户、端到端任务、关键假设、试用方法、继续/调整/停止条件 | 第一版随便少做几个功能 |
| 交付增量 | 本轮能验收什么结果？ | 用户完成一个业务闭环，或明确的技术风险得到验证 | 先做完所有前端 |
| 实施任务 | 下一步具体改什么、怎么验证？ | 有输入、依赖、修改边界、产物和完成条件 | 完成后端开发 |
| 子 agent 工作单（可选） | 哪一块可以独立执行并收回检查？ | 引用已就绪任务，给最小上下文与返回要求 | 把整个项目扔给多个 AI |

MVP 不是每个任务的名称；已有产品的小功能通常直接拆增量。实验、技术探针和演示原型可以验证局部假设，但须明确其简化内容，不能直接认定为可生产交付的 MVP。减少功能范围不能取消必要权限、安全、数据完整性和恢复措施。

T03 先列“本轮必做、可延后、明确排除”，再按业务价值、紧迫约束、风险和依赖排序。依赖缺失的高优先级任务不能直接开工，应先安排解除依赖。评分只用于辅助比较，不制造没有依据的精确分数。

## 2. 把计划写成可验证的里程碑

里程碑描述结果、证据和进入下一步的条件，不写“完成 80%”。按项目需要选择下列节点，可合并，不要求每个项目拥有全部节点。

| 里程碑示例 | 可观察的完成条件 | 已有记录 |
|---|---|---|
| 关键假设有结论 | 试验/研究回答了明确问题，说明证据限制和后续决定 | T02/T03/T05 |
| 当前增量可实施 | 需求、契约、体验与验收条件一致；关键依赖可用 | QG-01、T08 |
| 最小端到端路径接通 | 用户输入经界面、接口、业务与存储返回可核对结果；按实际系统删减层级 | T07；有模拟依赖时标明范围 |
| 当前增量已验收 | 目标范围在集成版本上通过，缺陷和例外按规则处理 | QG-03、T12 |
| 本轮交付关闭 | 交付说明、证据、已知问题和后续行动可恢复；发布项目另完成发布检查 | T09/T10/T12 |

设计交付项目的里程碑可以是可审查的设计包和契约，不以实际写代码作为完成条件。预计日期用于预测与协调；调整时记录原因、影响和范围取舍，不把日期到达自动当作通过。

## 3. 排依赖，并先验证最危险的假设

1. 每个 T08 任务写清依赖项、所需输出版本和解除依赖的证据。列出共享接口、数据结构、配置和外部输入。
2. 先处理会阻断多条后续路径的依赖，以及失败后需要大规模返工的假设。无关键风险的任务直接推进，不为形式新增试验。
3. 对未知能力做有时间预算的探针：问题、方法、预算、成功/失败判据、退出后的决策。到期仍无结论就记录未知，选择缩小试验、替代方案或获取关键输入；不能无限续跑。
4. 尽早接通一条最小端到端路径，再扩展异常和其他场景。接通证明集成可行，完整验收仍按 T07/T12 执行。
5. 外部能力不可用时可采用明确的模拟契约推进独立工作；真实集成仍保持待验证。循环依赖先调整任务边界或契约，不能互相标记“等待对方”。

## 4. 就绪后开工，限制同时进行的任务

T08 的就绪检查：目标可判定、权威输入可定位、依赖满足或明确隔离、修改范围清楚、验证可执行、所需授权有效。不要求提前解决所有实现细节。

推荐任务状态：待整理 → 就绪 → 进行中 → 待集成/验证 → 完成；另设阻塞、取消。任务状态描述工作推进，不替代主流程中的成果状态；一个技术探针完成，不表示产品已验收。

- 开始处理时记录开始时间；完成适用集成和验证后记录完成时间。
- 已开始但未完成的任务计入在制工作，包含阻塞和待验证项；不能移到“阻塞”列来隐藏积压。
- 在 T08 定义当前同时推进上限，依据执行和验收能力设定。初次试点可从较低并行度开始，出现积压先结束、解阻或整合现有任务。
- 任务过大时沿可验证结果切分；不为提高完成数量切成没有独立意义的碎片。
- 插入紧急事项时记录理由、被推迟事项和恢复安排，不悄悄扩大当前迭代。

只借鉴看板的透明状态、控制在制工作与主动解除阻塞等实践，不宣称实现了完整看板体系。[The Kanban Guide 2025.5](https://kanbanguides.org/the-kanban-guide/2025.5/) 还定义了相应度量要求。项目可从任务开始/完成时间、阻塞时长与返工记录判断拥堵；不将任务数用于个人能力排名。来源登记为 SRC-31。

## 5. 何时用子 agent

任务多只是候选信号。具备以下条件才值得拆分：运行环境允许、工具确实支持；输入和接口稳定；可划清修改边界；结果可独立检查；并行收益能覆盖上下文、审阅和集成成本。当前环境的授权与工具规则始终优先，本文件不能授予启动 agent、数据外发或生产操作权限。

适合并行的例子：已有稳定契约下的不同模块实现；限定范围的资料核查；针对已固定版本的检查；**以及针对 D0/D1 权限资金、数据迁移与发布前版本的“独立上下文交叉审计子 agent”（见 STD-QA-12）**。涉及同一状态机、同一迁移、共享核心接口或密集修改同一文件时，优先顺序执行，或先完成共享契约。没有子 agent 能力时按同样任务卡顺序实施，高风险审计改用新开独立对话窗口完成，流程仍成立。

一次委派复用 T08，并至少附上：

| 字段 | 必需内容 |
|---|---|
| 目标与边界 | 任务 ID、一个可判断结果、明确不做的内容 |
| 输入版本 | 必要需求/规则、契约、相关代码、工作流版本及既有决定；前端附 T06 视觉基线/授权新方向、设计变量、组件库版本 |
| 修改权限 | 可修改文件/模块、共享文件处理方式、禁止外部动作 |
| 依赖与接口 | 前置结果、输出结构、调用约定及当前有效版本 |
| 验证与返回 | 实际产物、变更清单、运行过的检查及原始结果、未运行项与问题 |
| 预算与停止 | 时间/调用或成本边界；缺关键答案、契约冲突、权限不足时停止依赖部分并返回 |
| 集成安排 | 谁收回检查、集成顺序、隔离位置及冲突处理；不是新增专业岗位 |

上下文只提供完成任务必要且获准使用的材料；不得将凭据、无关个人信息或生产数据默认发给子 agent。跨电脑交接提供真实文件、版本和说明，不能假设对方能读取本地路径。

移动项目同时附 T13 任务模式（模式 A 既有 App 修改对接 vs 模式 B 从 0 新建 App）、平台/能力/设备矩阵与 [08](08_移动App专项.md) 的适用规则。共享业务契约（`contracts/`）、原生桥接、主题、数据库迁移和签名配置分别明确修改归属；子 agent 不获取签名秘密。平台任务收回后逐平台集成与验证，不把共享代码通过视为两端通过。

## 6. 收回、集成与失败处理

1. 核对返回内容是否齐全，读取实际文件和差异。另一个 agent 的通过标签不能替代证据。
2. 对照原始任务、契约、授权边界和检查结果，识别额外改动、依赖变化与未运行项。不合格结果退回具体修复项，保留原问题。
3. 前端并行线复用同一 T06 视觉基线或已授权新方向；主题、设计变量、全局样式和基础组件明确修改归属，不允许各自另定审美。避免多个写入任务同时改动共享文件；按需要使用不同工作目录或分支。隔离工作区也不能消除语义冲突，合并前仍检查版本和契约。
4. 按依赖顺序集成小批量变更，重新验证受影响路径；各分支单独通过不代表整合后通过。整合后必须重跑 CI 四道硬门禁（`verify-gates.mjs --all` + PostgreSQL 集成测试，STD-QA-13），并更新合并后 Commit 的 SHA-256 指纹锁（STD-AUD-07），再应用 QG-02/QG-03 归入 T07/T12。
5. 契约或需求变化时暂停受影响的子任务，更新版本与影响范围后重新分派；未受影响任务继续。超时、部分返回或工具失败要明确保存现场，再选择续接、重派或自行完成，避免重复执行外部副作用。
6. 单项任务完成与整轮目标完成分别判断。集成后的验收结论由当前执行链核对，不由子任务数量或成功率推导。

## 7. 阻塞、变更和收尾

阻塞发生就写入 T08：是什么、阻塞哪些任务、已试过什么、需要哪个具体输入/决定、下一行动及复查时间。只暂停依赖部分；不得把用户未回复视为批准，也不反复申请已授权的同一事项。

需求或范围变化写入 T10：变化原因、受影响需求/契约/测试、工期或质量影响、取舍与决定依据。授权范围内的普通实现细节自主处理；改变业务结果、验收条件、权限或不可逆后果的缺口才获取必要决定。验收失败后不能降低原条件来伪造完成。

每轮收尾核对：

- 预定结果是否已实际验证；不把“代码写完”当作交付完成。
- 发现项是否修复并复验；允许的例外是否有影响、依据、期限和后续任务。
- 新增范围、取消项和剩余风险是否已登记；完成项不能掩盖未完成的目标。
- 当前版本、文件、关键决定、未完任务和下一动作是否进入 T10/session_handoff。

## 8. 工单案例中的用法（仅示意，未执行）

先确定当前增量是“创建工单、查看授权范围内工单、处理后关闭”，排除通知、附件和复杂分派。是否构成 MVP 取决于是否安排了真实目标用户试用及假设判断，不能仅因范围小就称为 MVP。

先统一创建、查看、关闭的状态与权限契约，再接通创建后的可查询结果，随后完成授权查看和关闭。并发重试、越权访问、关闭冲突继续按案例原有用例验收，不能因做最小范围就删除。

如真实项目允许且工具支持，可把稳定契约下互不冲突的任务交给子 agent；共享权限逻辑和迁移由明确的一条执行链修改。所有结果回到同一集成版本检查。任务、里程碑与验收状态仍为未执行，本文不产生新的通过记录。
