# 移动 App 设计、开发与交付专项

版本：1.1.0｜适用：iOS/iPadOS、Android 原生及既有/新建跨平台移动 App。手机浏览器页面仍按 Web 路径（React + Preline UI）。HarmonyOS、国内各安卓商店、企业分发及其他平台需在 T13 登记其官方规则，不能套用 Google Play 得出上架结论。

本专项严格区分**两种工作模式**，先在 `S0` / `T13` 判定后再调用对应分支：
- **模式 A（默认常规路径）：既有移动 App 修改、优化与接口对接**——当团队已有移动 App 工程，只需调整界面交互、修复缺陷或对接后端通用契约包（`contracts/`）时启用。严禁借优化之名推翻重写原工程。
- **模式 B（条件调用路径）：从 0 到 1 新建移动 App**——**仅当明确立项新建移动 App 时才调用本分支**，执行完整平台选型、生命周期架构、设备矩阵与商店首次提审准备。

沿用 S0–S9，不增加团队岗位。唯一必做规则见 STD-MOB-01 至 STD-MOB-16；本文件提供应用方法，T13 汇总移动端范围并引用 T05/T06/T07/T09/T12 的权威记录。没有的能力不必开发，严禁选用 `uni-app` 或 `Capacitor`。

## 1. 各阶段怎样接入（按模式 A / 模式 B 路由）

| 阶段 | 模式 A：既有 App 修改优化与契约对接（常规） | 模式 B：从 0 新建 App（仅立项新建时调用） | 记录与出口 |
|---|---|---|---|
| S0–S2 | 盘点既有工程版本、目标系统、已接组件与本次局部改动/对接需求；禁止扩大改版范围 | 确定目标平台、最低支持系统、设备窗口、语言地区、分发渠道、核心联网/离线场景与质量预算 | T13 模式判定与范围，T03 需求与 `AC` |
| S3–S4 | 直接消费服务端 `contracts/openapi-baseline.yaml` 与 `base-contract.schema.ts`，核对错误码、幂等指纹（`STD-API-08`）及与服务端支持窗口兼容 | 设计本地与服务端数据、前后台/杀进程生命周期、权限清单、同步与兼容策略；按 `STD-ARC-09` 比较 **React Native + TS** 与原生方案 | T04/T05 契约、ADR（模式 B）、T13 能力清单 |
| S5 | 严格遵守 `STD-FE-05` 继承既有 App 风格与原生导航习惯；仅在明确授权改版时按范围调整 | 建立移动产品视觉方向，适配安全区域、手势返回、系统栏、键盘、字体放大与无障碍 | T06 移动交互/视觉；设计验收不冒充真机验证 |
| S6–S7 | 测试先行（`@req/@ac`）并按 `STD-QA-11` 做改前/改后基线对照，在真机验证新增对接接口与受影响页面 | 按业务闭环实现，建立完整设备/系统/版本矩阵，真机实测恢复、弱网、权限拒绝、深链与性能 | T07 用例/黑盒证据、T12 发现与指纹锁 |
| S8–S9 | 随现有发版节奏增量更新签名包，核对兼容旧版本客户端与灰度监测 | 完成首次签名配置、隐私清单/第三方 SDK 披露、商店素材、渠道政策核对、首次提审及灰度运行 | T09 发布记录、T12 结论、T10 交接 |

## 2. 技术与平台选择（模式 A 沿用 vs 模式 B 新建）

- **模式 A（既有 App 修改与接口对接）**：默认**完全沿用既有移动仓库的技术栈**（如原生 Swift/SwiftUI、Kotlin/Jetpack Compose、已有 React Native 或 Flutter 工程），不得借局部优化强行替换底层框架。重点通过 [openapi-baseline.yaml](contracts/openapi-baseline.yaml) 与 [base-contract.schema.ts](contracts/base-contract.schema.ts) 对齐请求/响应模型、统一错误码（401/403/404/409/422）与 `requestId` 幂等重试逻辑（参考 `SRC-46`）。
- **模式 B（仅从 0 新建 App 时调用）**：在 T05 中针对当前关键场景比较跨平台与原生方案。默认优先评估与团队 Web 黄金栈同源的 **React Native + TypeScript**（`SRC-50`，便于复用 TypeScript 契约、Zod 校验与 Zustand/TanStack Query 逻辑）；若涉及重度原生图形、高频相机帧或复杂硬件通信等硬约束，比较 iOS（Swift）/ Android（Kotlin）原生方案，先用最危险的一条路径验证关键原生模块与系统版本支持。**本工作流禁用 `uni-app` 与 `Capacitor`。**

共享业务术语、接口契约与设计变量；按平台实现导航、权限、输入与后台能力。不要把桌面 Web 页面直接等比缩小当作移动设计。跨平台不免除 iOS 与 Android 两端真机验证；原生代码也不自动保证质量。桥接层声明线程、资源生命周期、错误和取消；依赖升级按原生影响重新判断。

## 3. 交互、视觉与设备适配

修改任务遵守 STD-FE-05：默认继承产品风格，用户明确改版或换库则按范围实施。产品内品牌一致和平台行为适配同时考虑，不要求两端逐像素相同。

T06 至少为实际支持范围说明：导航层级、返回/关闭含义、手势与按钮替代、安全区域和系统栏、键盘弹出后的表单/操作可达性、文字放大、屏幕阅读顺序与标签、触控目标、横竖屏/窗口变化、深浅主题、本地化长文案。使用语义颜色表达状态并辅以文字，不仅靠颜色或手势。

布局依据可用窗口与内容调整；平板、折叠屏、多窗口是否支持由范围决定，不以设备品牌代替适配定义。记录适用平台建议的尺寸单位及依据，不把 CSS px、pt、dp 混作相同物理尺寸。Apple HIG 与 Android 自适应指南分别见 SRC-34/38；具体数值按选定组件和系统版本核验。

## 4. 生命周期与状态恢复

将瞬时界面状态、需保留草稿、已提交业务事实和敏感缓存分别管理。定义切到后台、锁屏、中断、系统终止进程、再次启动、配置变化后哪些内容恢复、重新请求或清除。不要依赖“退出时一定执行保存”或内存变量永久存在。

恢复时重新确认身份、权限和服务端状态，不自动重放未知结果的付款、提交或删除。网络超时后复用操作标识查询/幂等重试；后台任务按平台允许方式调度，明确可延后、过期与取消，不承诺定时器在后台持续运行。iOS/Android 生命周期依据见 SRC-35。

## 5. 权限、登录与本地安全

每项系统能力登记用途、最少权限、触发时机和替代路径。优先判断系统选择器能否满足需求；在用户使用相关功能时解释和请求，区分未请求、允许、限制/部分允许、拒绝、撤回，以及该系统提供的其他状态。返回前台按需重新检查。拒绝照片/通知等非必需能力时仍能使用其他功能，不反复弹窗施压（SRC-36）。

系统权限不等于服务端业务权限或所有隐私处理的授权。登录令牌按平台安全存储方式保护，iOS 可用 Keychain；Android 按需要使用 Keystore 保护密钥和受保护存储，不把 Keystore 描述成任意业务数据仓库。服务端密钥不得打包进客户端。

核对日志、崩溃报告、备份、剪贴板、截图/任务切换预览、缓存和 WebView 是否暴露敏感内容；按实际风险保护，不强制普通内容禁止截图。退出/切换账户后隔离缓存、草稿、待同步队列和通知关联，旧账户请求结果不得写入新账户界面。生物识别只是本地认证能力，不能取代服务端授权。依据 SRC-39/40，按实际控制项映射验证，不声称扫描通过即安全认证。

## 6. 弱网、离线与数据同步

首先选择每个操作的模式：仅在线、离线只读、离线草稿或可排队提交。不强制每个 App 离线优先。

需要离线写入时，T04/T05 明确本地数据版本、事实来源、操作 ID、队列持久化、重试/退避/过期、取消、冲突、身份失效和失败恢复。区分“本地已保存”“待同步”“服务器已确认”；不向用户虚报成功。冲突按业务决定拒绝、合并或人工处理，不能对资金、库存等重要数据默认采用最后写入覆盖。断网重连、超时、重复、乱序及进程重启后验证最终数据和副作用数量。离线设计依据见 SRC-37。

本地 Schema 升级也属于迁移：从受支持旧版本升级、已有草稿/队列保留、磁盘不足和迁移中断需有处理；不能简单清库伪装修复，尤其不能丢弃未同步用户数据。

## 7. 通知、外部入口及条件能力

| 能力 | 必须明确的行为 | 验证重点 |
|---|---|---|
| 推送/本地通知 | 授权、token 更新、退出解绑、隐私文案、重复/迟到/不可达与偏好 | 不依赖通知必达；打开后查询权威状态，失效内容有反馈 |
| 深链/分享/外部 Intent | 允许的协议/域名/路径/参数、未登录续接、无权/无记录、冷启动导航 | 外部参数不可信；跳转后重新授权，链接不能直接触发高影响写入 |
| WebView/原生桥接 | 可信内容范围、导航控制、桥接口权限与数据校验 | 不把高权限桥暴露给任意网页；拒绝不可信输入 |
| 相机/定位/媒体/蓝牙等 | 选定平台的权限、资源占用、后台限制与替代路径 | 拒绝/撤回、硬件不可用、中断、资源释放；按需补官方能力专项 |
| 支付/订阅 | 地区/渠道规则、购买状态、服务端确认、重复回调、退款/撤销与恢复权益 | 不凭客户端成功回调授予永久权益；只在存在此业务时启用 |

入口设计可参考 Android App Links（SRC-43），iOS 的具体 Universal Links 配置需在实际项目读取相应官方说明。支付、广告/追踪、未成年人、用户生成内容、账户删除等按功能和地区核对渠道现行政策，不默认要求所有 App 增加账户或支付。

## 8. 性能与设备验证

T03/T13 定义冷/热启动、关键交互响应、滚动卡顿、内存、崩溃/Android ANR、流量、电量、包体积及存储预算中适用的项。记录目标设备、系统、负载、网络、样本和测量方法；无实测先标预算或待验证，不复制任意通用阈值。性能依据见 SRC-44。

模拟器用于快速反馈，不能替代硬件、性能、耗电、系统权限和渠道安装场景的全部证据。每个实际交付平台至少在风险选择的代表性真机验证关键链路，记录最低支持系统/主流系统、设备能力/屏幕、网络与安装版本覆盖及缺口；不要求跑完整笛卡尔积。使用接近发布的构建，调试版数据不自动代表发布性能。双端共享代码不等于只验一个平台。

## 9. 发布、兼容与持续运行

移动端不能假设所有用户立即升级。T05 定义服务端支持的客户端版本窗口、字段/能力兼容、弃用与升级提示；数据库与 API 变更检查仍在支持期的客户端。强制升级须有业务依据、可用下载渠道及失败恢复，不把它作为所有兼容问题的默认解决办法。

T09 保存 bundle/application ID、版本/构建号、代码/制品摘要、构建工具链、签名身份引用、分发环境、端点/开关、符号文件或混淆映射位置。签名私钥和口令不放文档或交给子 agent；到期/更新及保管方式可追溯。验证新安装和覆盖升级，不能只验证开发器直连安装。

提审前按渠道核对：开发者身份与资格、系统/SDK/target 要求及生效时间、商店素材、功能可访问性、审核所需演示方式、隐私政策与数据披露、第三方 SDK 行为、适用权限声明/隐私清单、账户与支付等功能政策。声明必须与真实构建和运行行为一致；Apple 隐私披露包含集成第三方伙伴的数据行为（SRC-41），不能只看自有代码。

App Store 与 Google Play 官方入口见 SRC-41/42。不同国家/地区和其他商店另建渠道行，填写实际官方链接、访问日期、适用条目、生效时间、验证结果。本文不固化易变的 SDK 数字、审核周期或支付政策；未知要求应阻塞该渠道发布准备，不影响独立设计开发。

发布计划包括小范围分发、观察窗口、崩溃/关键任务等停止阈值、接收与处置安排。暂停灰度或下架不能卸载用户已安装版本；故障处置分别考虑服务端兼容、已有功能开关、停用高风险能力和提交修复版，不能承诺任意客户端降级。线上日志应可关联构建版本，崩溃需能符号化/还原调用位置，证据脱敏保存。

## 10. 可直接用于 T07 的验收场景

以下为待项目细化的场景，不是已运行测试；阈值、数据和证据填写 T07/T12。适用关键场景未通过，按现有缺陷等级阻塞相应交付。

| 场景 | 操作 | 预期和证据 |
|---|---|---|
| 权限拒绝/撤回 | 拒绝能力请求，或设置中撤回后返回 | 相关功能可解释地降级，无崩溃、越权访问或持续弹窗 |
| 草稿被中断 | 填写后后台终止进程并重启 | 按契约恢复/清除，敏感数据保护；不是仅恢复截图 |
| 提交结果未知 | 服务端可能成功时断网，再恢复/重启 | 查询或幂等重试，数据/副作用不重复，UI 不虚报成功 |
| 多端或离线冲突 | 制造旧版本写入/队列重放 | 按契约拒绝/合并，保留用户可恢复信息 |
| 账户隔离 | 有缓存和待同步项时切换账户 | 新用户无法读到旧数据，旧请求不污染新会话 |
| 外部入口 | 冷启动/登录过期时打开合法和恶意链接 | 路由与返回合理，重新授权，非法参数安全拒绝 |
| 视觉与无障碍 | 键盘弹出、文字放大、屏幕阅读、支持的窗口/主题变化 | 内容操作可达，焦点和标签有意义，与 T06 方向一致 |
| 升级与兼容 | 旧安装含数据升级；旧客户端访问新服务 | 数据迁移和支持窗口内行为正确，失败有恢复路径 |
| 发布构建 | 从选定测试渠道安装准确制品，执行核心链路 | 配置/签名/版本正确，有真机和运行证据；商店审核另记 |
| 性能与恢复 | 代表性低能力设备/弱网及中断条件下操作 | 满足预算，未知项留待验证，失败可定位到构建 |

## 11. 工单案例的移动扩展（示意：模式 A 对接 vs 模式 B 新建）

- **若按模式 A（既有内部 App 对接工单功能，常规首选）**：不重建 App 壳子。在既有 App 中读取 `openapi-baseline.yaml` 与 `API-001~004` 契约，在对应页面模块复用已有网络客户端与登录态，遵循原有 UI 风格增加“提交工单”入口；创建时传入客户端 UUID `requestId` 并由服务端按 `STD-API-08` 校对载荷指纹，超时重查 `API-002` 或同 ID 重试，测试按改前/改后基线在真机复验核心链路。
- **若按模式 B（明确从 0 新建工单 App，条件调用）**：调用本专项新建分支，在 T05/T13 优先评估 **React Native + TypeScript**（复用 `shared/contracts/ticket.schema.ts`），并在 T13 补齐前后台状态恢复、断网受保护草稿、账户切换隔离缓存、以及 iOS/Android 双端设备矩阵与商店提审核对，先跑通“创建→查看结果”最小真机路径，旧 Web 案例的预期用例不算移动端通过证据。
