# 工程质量与审计验收基线

版本：0.9.1｜适用：零开发经验团队开展软件项目的设计、实现、黑盒验真、索引树与 CI 门禁、指纹审计和验收。沿用每位成员全栈推进的方式，不增加专门岗位或培训阶段。

本文件把成熟标准和实践转成项目执行方法；唯一规则编号与必做动作在 [规则库](01_规则库.md)。各项目按触发条件启用，将结果放入现有 T05/T07/T09 和新增 T12，不为每条原则单独建立文档。

## 1. 标准的性质与采用边界

| 类别 | 主要参考 | 本工作流如何使用 |
|---|---|---|
| 正式标准/协议规范 | ISO/IEC 25010:2023、ISO/IEC/IEEE 42010:2022、29119-2/3:2021、W3C WCAG、HTTP RFC | 质量范围、架构描述、测试过程与文档、可访问性及接口语义；按实际适用项采用 |
| 行业组织框架/规范 | OWASP ASVS、NIST SSDF、OpenAPI | 安全要求、开发过程和接口契约；记录版本与适用条目 |
| 成熟工程实践 | 关注点分离、单一职责、封装、适度复用、C4、ADR、小批量和持续集成 | 转成模块约束、决策、自动/人工检查与证据 |
| 语言或工具约定 | PEP 8、Google 风格指南、TypeScript、ESLint、React、Preline UI、Prisma、Playwright | 只在选定技术栈中使用，新建项目默认采用团队黄金栈 |
| 本团队执行约定 | 下面的检查节点、缺陷分级、证据字段与例外规则 | 用于实际项目推进，不冒称国际标准逐条要求 |

来源与核查范围见 [05](05_来源与更新机制.md)。ISO 本轮只核查官方公开摘要，没有读取付费全文；本文不提供 ISO 条款级映射或符合性结论。42010 约束的是架构描述，不能仅凭画了架构图证明架构质量。

## 2. 在项目中确定质量基线

S2 定义业务结果和质量场景，S4/T05 确定实现约束，S6/T12 固定适用检查与通过条件。项目已有有效标准直接引用，新增约定只覆盖缺口。

至少明确：适用规则及版本、语言与框架、风格/类型/静态检查、构建方式、关键风险与测试层次、性能与可靠性目标、审计证据和例外。产品没有某项能力时，不为满足检查表而新增它。

质量要求必须可观察：例如“给定规定的数据量和并发，对指定请求测量 p95 延迟与错误率”；具体预算由项目决定。功能正确、可靠性、安全、可维护性、交互和性能等维度按风险选择；这是项目检查清单，不是对 ISO 25010 全部分类的转载。[ISO 官方摘要](https://www.iso.org/standard/78176.html)

没有通用的“函数最多 30 行”“覆盖率必须 100%”“所有接口必须 200ms”保证质量。项目可设置有依据的阈值；工具分数只提示风险，不能抵消业务或安全失败。

“最优”指在本次用户目标、质量约束、成本和维护能力下有证据支撑的选择。满足必要条件后，优先简单、可理解且可验证的方案；未发现实质收益时不增加抽象层、服务、组件库或装饰。记录重要取舍即可，不为普通实现搜寻无限备选。代码评审也应区分必须修复与可选润色，参考 [Google 评审标准](https://google.github.io/eng-practices/review/reviewer/standard.html)。

## 3. 架构质量：怎样设计，怎样检查

对应 STD-ARC-01 至 STD-ARC-09、STD-BIZ、STD-DAT、STD-API。新建项目无既有仓库约束时，按 STD-ARC-09 默认采用**团队黄金技术栈**（Web 前端 React 18/19 + TypeScript strict + Vite + Tailwind CSS + Preline UI〔或按需 Meta StyleX/Lexical 生态〕+ Zustand/TanStack Query；后端 Node.js LTS + Hono/Fastify + TypeScript + Zod；数据库**统一采用 PostgreSQL 16 + Prisma ORM**，**严禁使用 SQLite**；移动端默认采用既有 App 修改优化与契约对接，仅明确需从 0 新建 App 时调用新建分支评估 React Native + TS 或原生方案），避免零经验成员在框架选型上各自发散；仅当黄金栈经验证无法满足硬约束时通过 ADR 申请偏离。

### 3.1 最小必要架构描述

新系统或结构调整时，在 T05 保留以下适用内容：系统边界、模块与数据归属、关键调用路径、部署与外部依赖、重要质量约束、关键决策及风险。已有系统只更新受影响部分。

图中标明名称、职责、关系方向、关系含义和适用版本；文字、图、代码与契约使用同一业务术语。一个标注含糊的“服务层”方框不能代替接口与职责说明。

可参考 C4 的分层表达；按沟通需要选择层次，不强制四层齐全，C4 的 container 也不专指 Docker。[C4 官方说明](https://c4model.com/diagrams)

### 3.2 将常见原则转成可执行检查

| 原则 | 项目动作 | 应警惕的情况 |
|---|---|---|
| 关注点分离、职责集中 | 让不同变化原因的业务规则、界面展示和基础设施逻辑有清楚边界 | 一个页面同时处理权限、费用算法、数据库和通知 |
| 封装与低耦合 | 模块通过约定入口交互，内部状态不由其他模块任意改写 | 改一个字段必须同步修改多个无关模块；跨模块直接改私有表 |
| 单一职责 | 将围绕同一业务目的变化的逻辑放在一起；清楚说明模块职责 | 仅按行数拆函数，拆完反而难以理解完整行为 |
| DRY／适度复用 | 同一规则维护一次；相似但含义不同的行为允许独立 | 复制核心计算；或将不同业务硬塞进大量开关的万能函数 |
| 简单设计、避免过早扩展 | 用满足当前约束的最小结构；对预期扩展记录触发条件 | 没有实际需求先建插件平台、微服务或通用流程引擎 |
| 依赖可替换、便于验证 | 在外部系统、存储等实际变化边界提供清楚的适配入口 | 为每个简单类机械建立接口；或测试核心规则必须连接所有外部系统 |

这些原则的选择性应用可参考 [Microsoft 架构原则](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/architectural-principles)，不是要求项目采用 .NET、Clean Architecture 或某种固定目录。

### 3.3 架构验收必须有场景

- **结构：** 调用和数据归属符合声明；新增越界访问、循环依赖有检查结果。
- **业务：** 核心不变量成立，例如重复请求不重复扣减、无权用户不能读取他人数据。
- **失败：** 已识别的超时、并发冲突、依赖不可用有确定结果及恢复方式。
- **质量：** 重要质量场景有试验或实现证据；估算与实测分别记录。
- **演进：** 对本次真实预期变化列出影响模块，验证契约兼容与迁移路径；不为所有想象中的未来预建能力。

工具能低成本检查的边界可以自动化；不能自动检查的用明确人工步骤，不为“架构验证”先开发复杂平台。

## 4. 代码质量：开写之前与提交之前

对应 STD-CODE-01 至 STD-CODE-10。以下是团队执行细则，可参考 [Google 代码评审实践](https://google.github.io/eng-practices/review/reviewer/looking-for.html)，不要求另设评审岗位。

### 4.1 开写前固定项目约定

在 T05 记录已有或选定的风格指南、工具版本、配置文件和检查命令。JS/TS 可采用兼容项目的格式化工具与 ESLint；Python 可参考 PEP 8 并选用项目现有检查工具；其他语言沿用其生态和仓库约定。不要同时运行配置互相冲突的格式化工具。

TypeScript 项目默认建议 strict；旧项目采用渐进方式处理历史问题，不能为新增代码通过而全局关闭检查。其他语言不强行引入 TypeScript 或相同配置。

修改任务在开写前建立相称的行为基线（STD-QA-11）：逻辑缺陷先记录复现和正确预期，重构明确保持哪些行为，性能优化固定可比较的环境与负载。已有测试先运行相关部分，历史失败单列。历史行为和截图仅证明旧状态，不自动定义正确答案；预期应来自有效需求或明确的变更决定。不能为了基线检查覆盖他人未提交修改，无法安全复现时保存限制并安排替代验证。

### 4.2 针对实际差异检查

| 检查面 | 需要确认的实际问题 |
|---|---|
| 语义与命名 | 函数名与实际行为一致；变量能体现业务含义；金额、时间等单位明确 |
| 接口与类型 | 输入、返回、可空值、错误语义清楚；外部数据有运行时校验 |
| 复杂度与复用 | 主路径可读，重复业务规则已集中；没有为单次使用建立无必要框架 |
| 状态与副作用 | 共享状态由明确入口修改；IO、数据库和纯计算的边界可定位 |
| 失败与资源 | 错误可追踪且不泄漏敏感信息；文件、连接、监听器及后台任务有结束方式 |
| 并发与异步 | 等待、取消、竞态、事务和重试符合契约；不会把过期结果覆盖新结果 |
| 可维护性 | 注释解释必要原因/约束；变更同步影响到的契约与文档 |

本次新增死代码或未使用依赖应清理；已有无关问题单列，不顺手扩大改动。对检查规则的抑制必须局部、可说明且可复核，不能用大量忽略配置换取通过。

### 4.3 零开发经验成员的本地环境与 Git 救生基线（对应 STD-CODE-11）

由于团队成员无传统开发背景，AI 在 S6–S7 推进实现时必须主动承担工程防呆与救生职责：

| 场景 | AI 与成员的标准配合动作 | 严禁出现的行为 |
|---|---|---|
| 启动前保存点 | 开工前由 AI 执行 `git status` 检查工作区，创建任务分支或提交当前干净状态作为基准点（记录 commit 哈希至 T08） | 在未保存状态的工作区直接大面积改写文件 |
| 小闭环快照 | 每跑通一个最小可验证闭环（如接口落库通过、表单渲染通过），立即提交一次 Git 快照（如 `chore(snapshot): TASK-001 step 1 passed`） | 连续修改十几个文件不保存快照，出错后无法局部回退 |
| 一键命令封装 | 在 `package.json` 及 T05 中固化单行命令：拉起同构库（`docker compose -f docker-compose.postgres.yml up -d`）、启动（`npm run dev`）、数据可视化（`npx prisma studio`）、四道门禁与测试（`node scripts/verify-gates.mjs --all && npm run check && npm test`） | 让零经验成员手工拼接冗长命令行或私自换用 SQLite |
| 密钥与环境隔离 | 提供 `.env.example`（含 PostgreSQL `DATABASE_URL` 示例），由 AI 自动校验 `.gitignore` 已排除 `.env`、`node_modules/`、`dist/` | 将真实密钥硬编码进源码或提交到版本库 |
| 改坏一键救生 | 当 AI 连续两次修复同一报错仍未解决或引发连锁崩溃时，立即停止盲目打补丁，协助成员回退至上一正常快照并缩小任务粒度 | 在错误方向上反复叠加生成补丁导致代码库彻底不可用 |

## 5. 接口、数据、界面和安全的共同底线

| 领域 | 应采用的执行基线 | 对应规则 |
|---|---|---|
| 接口 | 按 HTTP 语义设计方法/状态；继承通用契约包与载荷指纹；有错误、授权和兼容检查 | STD-API-01 至 STD-API-08 |
| 数据 | 事实来源清楚；PostgreSQL 唯一性与完整性在可信层执行；事务、迁移和恢复可验证 | STD-DAT-01 至 STD-DAT-04 |
| 界面 | 状态完整、React/Preline 组件契约清楚、设计变量一致；按适用目标检查无障碍与性能 | STD-UX、STD-FE、条件/默认启用 STD-REACT |
| 安全 | 威胁与数据范围、服务端授权、输入处理、密钥保护、适用 ASVS 条目及验证 | STD-SEC-01 至 STD-SEC-04 |
| 依赖与制品 | 可追溯的依赖版本、构建步骤、代码版本和制品摘要；升级有回归 | STD-CODE-09、STD-OPS-05/06 |

安全扫描、类型检查和可访问性扫描分别覆盖部分问题，均不能替代实际权限、业务和交互验证。HTTP 的幂等语义不自动实现业务去重；SemVer 版本号也不自动保证消费者兼容。

### 5.1 契约如何避免逐渐分叉

T05 指明精确结构由 Schema/OpenAPI 还是代码定义维护，以及类型、客户端和模拟数据的派生方向。已有工具能够可靠生成时优先复用，不为简单模块强建生成平台；人工维护也须有明确比对步骤。对真实生产方/消费方检查请求、响应、失败和边界。由同一错误契约生成的客户端和 mock 互相通过，仍不能证明真实服务或业务规则正确（STD-API-06）。

### 5.2 视觉设计：继承、允许变化、实际对照

对应 STD-FE-05/06、STD-QA-10，使用 T06/T07/T12。视觉是交付质量的一部分；功能正确、视觉一致、任务可用分别需要证据。

| 情形 | 应执行的动作 | 边界 |
|---|---|---|
| 修改/优化已有界面 | 读取现有页面与相邻路径、主题、设计变量、基础组件和交互模式；默认延续布局、字体、色彩、密度与反馈语言 | 不把“优化”解释为重新设计整个品牌；本次相关可访问性缺陷仍需修复 |
| 用户明确要求改风格或用其他组件库 | 记录请求及范围，按新方向继续；核对组件能力、主题、全局样式、键盘/焦点、体积和替换成本 | 已授权事项不再索要同一确认；组件库变化不自动授权其他页面全部改版 |
| 新产品没有既有风格 | 从用户任务、内容、品牌和终端确定方向，明确视觉层级、布局、字体、颜色、组件和状态 | 不强加固定配色、多字体、复杂动画或营销页结构；按真实内容设计 |
| 现有风格多套并存 | 先找当前模块有效约定和已确认目标，以最相关的相邻路径作为候选依据 | 没有足够依据且会改变重要视觉结果时获取必要方向；不擅自全站统一 |

GOV.UK 的贡献准则将适当复用既有风格和组件作为一致性实践；这里借鉴原则，不采用其品牌外观。[官方准则](https://design-system.service.gov.uk/community/contribution-criteria/) WCAG 的一致标识要求关注同功能组件的可识别性，不能推导为禁止视觉改版。[W3C 解释](https://www.w3.org/WAI/WCAG22/Understanding/consistent-identification.html)

实际检查顺序：

1. 记录旧页面或已授权新方向、精确版本和允许差异；无法查看原界面时只说明依据与限制，不能声称已完成匹配。
2. 在目标环境渲染，检查代表性宽度、主题及关键状态。用长文本、空数据、错误和有代表性的大内容检查重排、溢出、遮挡和信息层级；仅覆盖实际支持模式。
3. 对照同类/相邻页面，检查字体、色彩、间距、组件尺寸、图标、圆角、阴影和反馈是否符合方向。涉及全局样式或公共组件时扩展受影响范围。
4. 同时检查键盘、焦点、缩放/重排、文本对比和实际可操作性；截图不能替代这些检查，也不能证明后端正确。
5. 保存 T07 的渲染证据、环境、观察和差异。简单修改可人工对照；重复回归收益明确时才引入自动截图比较。固定浏览器、系统、字体、视口与数据，区分渲染噪声和真实变化；更新基线前检查每项差异，不能盲目接受全部变化。[Playwright 官方说明](https://playwright.dev/docs/test-snapshots)

设计包只验收原型/规格；实现交付必须检查实际渲染。没有运行条件时保持相关视觉项待验证，功能测试或构建成功不能替代。用户明确排除某类验证时记录请求、范围与剩余未验证项，不补造结果。

### 5.3 移动 App 验收入口

移动 App 按 [08](08_移动App专项.md) 和 STD-MOB-01 至 STD-MOB-16 执行：**模式 A（常规：既有 App 修改与契约对接）**重点核对既有视觉继承与通用契约包联调一致；**模式 B（条件：从 0 新建 App）**补齐平台生命周期、权限与上架核查。T13 汇总能力与设备矩阵；QG-01 检查前置能力/契约，QG-02 检查实际变更及中断恢复，QG-03 检查各交付平台的准确制品和代表性真机结果，QG-04 分开记录渠道审核与获授权发布后的观察。关键设备/权限/升级证据缺失时保持对应范围待验证，不以 Web 测试或单端通过替代。

### 5.4 通用契约包基线与幂等载荷指纹（对应 STD-API-07 / STD-API-08）

所有业务项目在 `S4` 必须直接继承 [contracts/](contracts/README.md) 中的 `base-contract.schema.ts` 与 `openapi-baseline.yaml`：
- **信封与错误码统一**：所有成功返回使用 `createApiResponseSchema`，所有失败使用统一 `ApiErrorResponse` 与标准 `ErrorCodeEnum`（`401/403/404/409/422/429/500/503`），避免 React 前端、Node 后端及既有移动 App 各自解析不同错误结构。
- **幂等载荷指纹**：所有携带 `requestId` 的写入接口必须调用 `computePayloadFingerprint`（对经 Zod 规范化并按键排序的 JSON 计算 `SHA-256`）随同 `requestId` 写入 PostgreSQL 去重表。若同一 `requestId` 重试时载荷指纹一致，安全重放原响应；若指纹不一致，立即返回 `409 IDEMPOTENCY_FINGERPRINT_MISMATCH`。

## 6. 将检查接入项目推进

以下节点是团队约定。先在 T05 写明工具和命令，再在 T12 固定适用范围。仅交付设计的项目止于设计验收，不虚构实现或运行结果。

| 节点 | 必查内容 | 可以得到的结论 |
|---|---|---|
| QG-01 设计可实施（S4–S6） | 需求与验收清楚，边界/契约无关键冲突，阻塞当前任务的关键前置风险已解决；可在实现中验证的质量目标有任务、条件及验证时点，尚未通过 | 相关任务可以进入实现；未验证的生产质量仍待验证 |
| QG-02 变更可整合（S7） | 相关格式/静态/类型/契约检查、代码差异评审、针对性回归通过；界面变更有实际渲染对照 | 该变更满足整合条件，不等于整个产品通过 |
| QG-03 增量可验收（S7） | 整合后准确版本通过适用构建、集成、核心路径及视觉检查，验收矩阵与缺陷清单完整 | 本次范围的实现验收结论 |
| QG-04 可发布及发布后确认（S8） | 授权、制品、配置、迁移、恢复、审计与运行检查；发布后验证真实关键路径 | 发布前准备通过与发布后运行确认分别记录 |

构建、测试与部署命令必须来自真实项目。工具不存在、脚本为空或步骤跳过时记“未运行/阻塞”，不能伪造绿色结果。无 CI 时运行等价的本地检查并记录环境，不能声称 CI 已通过。

小批量、经常整合并快速处理失败可以缩短反馈周期；参考 [DORA 持续集成](https://dora.dev/capabilities/continuous-integration/) 和 [小批量工作](https://dora.dev/capabilities/working-in-small-batches/)。子 agent 的局部结果必须在同一整合版本重新验证。本文件不因此启动多 agent，也不将并行数量作为质量指标。

### 6.1 零代码经验成员的黑盒可观察验真法与高风险复核门禁（对应 STD-QA-12）

零开发经验成员无法靠肉眼审阅代码 Diff 来发现事务漏锁、越权漏洞或假 Mock。因此，所有交付验收必须转化为**黑盒可观察操作**，并在高风险节点引入**独立复核门禁**：

| 验证对象 | 零代码经验成员可亲自执行的黑盒验真方法 | 合格证据标准 |
|---|---|---|
| 功能与持久化真实性 | 在浏览器完成真实表单提交后，运行 `npx prisma studio` 打开数据表界面，刷新页面并核对新增记录的字段值、状态与版本号 | 页面刷新后数据不丢失，Prisma Studio 表中记录与界面完全一致 |
| 跨角色/跨用户权限隔离 | 打开两个浏览器窗口（普通窗口登录用户 A，无痕窗口登录用户 B），在用户 B 窗口直接粘贴用户 A 的详情页 URL 或触发无权接口 | 用户 B 窗口显示无权/不存在提示，且浏览器 F12 → Network 中该接口状态码为 `403` 或 `404`（绝不能是返回 `200` 完整数据仅靠前端隐藏） |
| 重复提交与并发幂等 | 在浏览器 Network 面板开启“慢速 3G（Slow 3G）”或断网后连续点击提交、恢复网络重试，随后在 Prisma Studio 检查表记录数 | 只产生 1 条有效业务记录，无重复创建或报错崩溃 |
| 自动化测试与静态检查 | 在终端复制运行 AI 提供的单行命令（`npm run check && npm test`） | 终端末尾显示 `0 errors` 及全部测试 `passed`，且无被刻意跳过的用例（`skipped` 须有说明） |

**高风险独立复核门禁（Mandatory Gate）：**
当任务触及 **① D0/D1 权限与资金逻辑、② 破坏性或生产数据迁移（STD-DAT-04）、③ S8 生产环境发布** 时，执行成员完成上述黑盒自检后，**必须执行以下两项之一方可标记验收通过**：
1. **独立上下文 AI 交叉审计**：新开一个不包含此前开发对话历史的独立 AI 会话（或调用独立审计子 agent），仅传入需求契约（T03/T04/T05）与实际代码差异，指令其专门寻找越权、并发、注入与契约偏离漏洞；
2. **团队负责人复核确认**：将 T12 验收矩阵与关键黑盒证据交由团队负责人复核签字。

### 6.2 需求-验收-测试-编码四步闭环与 CI 四道自动化硬门禁（对应 STD-QA-01 / STD-QA-13）

为防止代码脱离需求野生生长或用跳过测试伪造绿灯，所有可运行软件项目强制实行**ATDD 四步闭环 + CI 四道硬门禁**（模板见 [ci/](ci/README.md)）：

1. **四步闭环纪律**：`REQ-xxx`（需求）→ `AC-xxx`（T03 结构化 Given/When/Then 验收条件）→ `TEST-xxx`（S6 先在测试文件头部写入 `// @req REQ-xxx @ac AC-xxx` 并运行确认未实现前失败 `RED`）→ `TASK-xxx`（S7 编码实现使测试转绿 `GREEN`，运行黑盒验真并回填 SHA-256 指纹关闭需求）。
2. **CI 四道自动化硬门禁**（[github-actions-ci.yml](ci/github-actions-ci.yml) + [build-index-tree.mjs](ci/build-index-tree.mjs) + [verify-gates.mjs](ci/verify-gates.mjs)）：
   - **Gate 1（闭环、索引树新鲜度与数据库同构门禁）**：检查测试文件是否全部绑定 `@req` 与 `@ac` 标签，拦截在 `schema.prisma` 中误用 SQLite，并校验 `PROJECT_INDEX_TREE.md` 与 `docs/index-tree.json` 是否已随最新代码变更刷新（`STD-GOV-05`）。
   - **Gate 2（静态质量、防作弊与技术栈净化门禁）**：执行 `prisma validate`、`tsc --noEmit`、`eslint`，自动拦截 `.skip` / `.only` / `xit`、空 `catch {}`、`.vue` 文件与 `package.json` 禁用旧栈依赖（`vue`/`element-plus`/`naive-ui`/`sqlite`/`uni-app`/`capacitor`）以及被跟踪的 `.env`。
   - **Gate 3（PostgreSQL 真实容器测试门禁）**：CI 自动拉起 `postgres:16-alpine` 容器，运行 `prisma migrate deploy`、Vitest 集成测试及 React 生产构建（按需加跑 Playwright）。
   - **Gate 4（三重指纹一致性门禁）**：校验契约目录、`schema.prisma`、依赖锁文件的 SHA-256 与已锁定证据指纹是否一致。

## 7. 项目审计：从结论追到原始证据

对应 STD-AUD-01、04、05、06；使用 T12。这里是项目自审和复核，不能对外称为独立第三方审计。

### 7.1 范围与证据链

开始时固定项目/增量、提交或制品版本、需求与契约版本、环境、采用规则、检查日期和排除项。审计既检查内容，也检查证据是否足以支持结论。

追溯：需求 → 业务规则 → 契约/界面 → 实现位置 → 用例 → 原始结果 → 缺陷/修复 → 复验 → 结论。

每项证据 EVD 至少记录：关联检查项、来源路径、采集方式、版本/环境/日期、实际观察、覆盖范围及敏感数据处理。重要制品可记录摘要；摘要只能检测内容是否与记录一致，不能单独证明事件真实发生、证据完整或采集者身份。

区分原始响应/数据核对、日志、截图、工具报告和人工判断。截图不能独自证明服务端授权或数据库正确；脚本退出码不能独自证明业务语义正确；模拟接口结果不能替代真实集成。

### 7.2 审计顺序

1. 核对版本和范围是否一致，过期报告不用于当前结论。
2. 检查需求到验收的覆盖，定位无来源实现和无验证需求。
3. 对关键业务、权限、数据一致性及不可逆行为逐项检查适用场景。
4. 对其余风险按记录的抽样方法检查；说明总体、样本、未覆盖范围。发现异常扩大相关范围，不从少量成功样本推断全部合格。
5. 建立 AUD 发现项，附违反的规则/预期、实际证据、影响和整改动作。
6. 修复后在新版本复验相关场景与受影响路径，留下修复前后的关联。
7. 形成范围明确的结论及残余问题，保存索引并更新交接。

审计发现不必另建复杂系统；用 T12 表格维护即可。发现无权访问、数据损坏等问题时按严重性阻塞受影响交付，其他独立任务可继续。

### 7.3 三重 SHA-256 指纹防伪与自动失效机制（对应 STD-AUD-07）

1. **契约与 Schema 指纹**：对 `shared/contracts/` 与 `prisma/schema.prisma` 计算 `SHA-256` 摘要。
2. **依赖锁与制品指纹**：绑定 `package-lock.json` 与构建产物哈希，确保测试环境与生产依赖一致。
3. **证据与 Commit 绑定（防过期）**：每次 T07/T12 验收通过时，须将 `verify-gates.mjs --gate=4` 输出的摘要连同当前 `git commit SHA` 写入 `fingerprint-lock.json` 与 T12。只要契约、Schema 或源码后续再改 1 个字节导致指纹漂移，此前验收状态自动降级为 **`Stale（指纹过期，待重验）`**，CI Gate 4 将直接阻断放行直至完成重验。

## 8. 软件审计日志：记录什么，怎样保护

对应 STD-AUD-02/03。项目按业务风险决定哪些事件需要审计，例如权限调整、重要状态转换、批量导出、关键数据修改和删除。普通调试日志与需要追溯的业务事件应区分。

字段候选：事件 ID、业务操作关联 ID、已验证的执行主体、动作、目标标识、服务端时间、结果、必要的前后状态/版本和失败类别。日志量与字段按用途最小化；不要记录密码、会话令牌、密钥或不必要的完整个人数据。[OWASP Logging 指南](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html)

项目必须明确：哪些动作需要与审计同事务提交；哪些允许可靠缓冲后汇集；日志写入失败时业务拒绝、重试或继续的条件。高影响动作不能在审计丢失时仍无依据宣称“全程可追溯”。不能对所有普通日志故障一律中断业务，也不能一律忽略。

验证至少包含适用的成功/拒绝/失败事件对应、重复事件识别、未授权读写限制、敏感内容检查、日志注入处理、采集失败告警与保留清理。按风险采用独立存储、追加写入、访问隔离或完整性检测，不强制所有产品使用同一种基础设施。

## 9. 验收范围、缺陷分级与结论

对应 STD-QA-08/09；使用 T12，原始用例仍放 T07。测试过程与文档可参考 ISO/IEC/IEEE 29119-2/3 的公开适用范围，下面的具体分级和表格是团队约定，不是 ISO 条文复刻。

### 9.1 验收维度

| 维度 | 在验收前明确的条件 | 所需证据 |
|---|---|---|
| 需求与业务 | 本轮关键用户路径和规则、不做项 | 逐项用例、真实业务结果；缺项明确排除而非隐藏 |
| 架构 | 边界、依赖、不变量、主要质量场景 | 架构差异、依赖检查、契约与关键试验 |
| 代码 | 项目风格、类型/静态规则、错误与资源处理 | 适用检查结果和实际差异审查 |
| 接口与数据 | Schema、权限范围、重复/并发、一致性和迁移 | 请求响应、数据核对、冲突与恢复场景 |
| 视觉、体验与可访问性 | 既有基线或授权新方向、目标终端、真实内容边界、关键状态与可访问性要求 | 改前/改后实际渲染对照、用户任务/人工检查、工具结果及未覆盖部分 |
| 性能与可靠性 | 测量环境、负载、样本、阈值、恢复目标 | 对应负载结果和适用恢复演练；不移用空库成绩 |
| 安全与审计 | 适用风险/控制项、关键事件、证据保护 | 越权与输入场景、审计事件、访问及敏感内容检查 |
| 发布与运行 | 版本、配置、迁移、回退、监测与授权 | 制品清单、发布前检查和发布后观察分开记录 |

范围选择由项目实际能力决定，不必每个小改动重跑全量。关键验收项必须事先识别，不能在失败后临时标为不关键。阈值变化作为变更保留原标准、原因和影响。

### 9.2 缺陷等级（本团队定义）

| 等级 | 判定依据 | 对交付的处理 |
|---|---|---|
| D0 严重 | 已发现或可复现的重大越权/泄漏、关键数据破坏、错误资金动作等重大后果 | 阻塞受影响发布与使用；先隔离风险和修复，不适用普通带缺陷放行 |
| D1 高 | 核心用户路径不能完成，重要业务结果错误或关键恢复要求不满足 | 阻塞本轮对应范围验收；确需排除功能须重新定义并验证交付范围 |
| D2 中 | 非核心功能异常，有明确可用替代，未破坏关键安全/数据/业务条件 | 可在已有授权内记录例外，写明影响、替代、修复任务与复核期限 |
| D3 低 | 不影响正确性和核心任务的轻微呈现/文案问题 | 进入后续待办；确认不属于被低估的可访问性或误导问题 |

按后果判断，不按代码行数或修复难度。安全缺陷还应结合适用风险模型，不用上述业务分级替代漏洞风险分析。

### 9.3 结论规则

- **通过：** 当前范围适用检查有有效证据，关键验收项全部满足，无 D0/D1，其他未解决项已关闭或明确不影响本次条件。
- **通过（有记录例外）：** 仅存在允许处理的非关键未满足项，已有明确影响、范围、替代措施、到期点、决定依据和授权；报告不得省略例外。
- **不通过：** 存在已证实的不满足项，且不符合例外条件。
- **阻塞/待验证：** 关键证据缺失、环境不可用、尚未运行或结果无法判断；不能计入通过。
- **不适用：** 该检查的触发条件确实不存在，记录原因；不是绕过失败的方法。

不要只报“通过率 95%”。至少分别报告适用项、通过项、有例外项、失败项、阻塞/未运行项与不适用项；一个关键失败不能被大量普通通过抵消。执行过测试也不等于有权发布。
