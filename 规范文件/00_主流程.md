# 软件产品设计与全栈交付主流程

版本：1.1.0｜适用：零开发经验团队开展软件产品设计与全栈交付，及已有软件功能迭代｜快速定位规则与模板见 [工作流索引树](INDEX_TREE.md)｜新项目一键脚手架见 [starter/](starter/README.md)｜生产部署基线见 [deploy/](deploy/README.md)｜所有强制条款均指本工作流内的团队规则，外部依据见 [来源登记](05_来源与更新机制.md)。

## 1. 目标与工作方式

把模糊想法变成有依据的需求、有边界的设计、明确的契约、可维护的实现，以及可复核的交付结果。产品设计负责用户与业务结果；全栈设计把结果连接到交互、数据、接口、权限、代码和运行方式。

流程可回退、可迭代。先设计并验证最重要的一条用户路径，逐步扩展。不要先写完整大系统文档再验证关键假设；也不要用“敏捷”跳过关键业务和安全决定。探索性原型可以早做，但须标识模拟数据、简化逻辑和不能用于生产的部分。

默认顺序：S0 启动 → S1 问题 → S2 范围与需求 → S3 业务逻辑 → S4 技术与契约 ↔ S5 体验与组件 → S6 实施准备 → S7 实现与验证 → S8 发布与运行 → S9 复盘。

高不确定性技术可在 S1–S2 提前做小规模可行性试验；先记录试验问题和判定条件。S4 与 S5 同步互相校正。每次需求变更均定位受影响步骤，而非全流程重做。

## 2. 每位成员的全栈执行方式

每位团队成员都以全栈产品设计师的方式，从问题理解持续推进到设计、实现验证与运行反馈。流程不按岗位划分阶段，不要求把成果交给另一个专业岗位才能继续。下文的“你”均指正在执行这项任务的成员，所有适用阶段和规则都由你贯通。

| 工作内容 | 需要完成的动作 | 完成依据 |
|---|---|---|
| 用户与业务问题 | 收集依据，确定范围、优先级与业务取舍 | 需求有来源，范围和成功条件明确 |
| 业务与体验设计 | 定义对象、规则、流程、交互和组件 | 正常与异常路径完整，关键决定有依据 |
| 技术与数据设计 | 比较方案、定义契约、复用能力、设计数据与安全边界 | 方案满足约束，契约可执行，关键风险有验证计划或结果 |
| 实现与验收 | 借助 AI 推进实现，检查差异，执行适用验证 | 实际行为与规格一致，有可复核证据 |
| 发布与持续改进 | 在授权范围内安排发布、监测、恢复与复盘 | 运行结果可观察，恢复步骤可执行，后续行动有依据 |

每轮按“读取现状 → 确定下一任务 → 完成产物或修改 → 检查结果 → 保存进度并继续”推进。以项目成果和验证结果判断完成，不安排默认授课、能力测评或复述作业。信息缺口转成调研任务，技术不确定性转成小试验，产物缺陷转成修复任务；必要解释只用于解决眼前的工作阻塞，或回应成员主动提问。

自检时先回到原始需求和预先写好的验收条件，再检查产物与实际结果，避免只验证自己实现的假设。针对零开发经验成员，验收采用**黑盒可观察验真法（STD-QA-12）**：通过浏览器真实交互、双无痕窗口越权测试、开发者工具 Network 状态码、Prisma Studio 数据库可视化核对及单行测试命令输出验证结果，不要求成员肉眼阅读底层代码差异。关键取舍直接记入现有决策或契约，不另写学习报告。日常任务不把岗位分离设为默认前置条件；但涉及 **D0/D1 权限资金边界、不可逆数据迁移（STD-DAT-04）或 S8 生产发布** 时，必须触发独立上下文的 AI 交叉审计会话或由团队负责人复核确认。记录执行成员用于追溯，不代表重新划分岗位。

全栈执行不扩大既有的业务决定权、数据访问或发布权限；超出已授权范围的决定仍需取得相应授权。软件内部的用户角色与权限（例如普通用户、管理员）仍须按业务需要设计，它们不是团队的工作岗位。

### 架构判断嵌入实际项目任务

架构设计贯穿需求、设计、实现和变更，不新增学习阶段。仅在影响系统边界、质量、依赖或长期成本的关键决定上展开下表；简单局部改动可简述依据。

| 推进到哪里 | 要完成的具体工作 | 记录到哪里 |
|---|---|---|
| S0–S2 定义问题与范围 | 明确目标、约束、排除项；把性能、成本、可靠性等重要要求写成可检查场景 | T01 启动卡、T03 蓝图与质量预算 |
| S3–S4 建立系统结构 | 列明系统边界、模块职责、数据归属、依赖方向；用一条完整业务路径串起调用与数据变化 | T04 业务规则、T05 架构与契约 |
| S4 做关键选择 | 比较现有方案与可行替代，记录选择、代价、关键假设和改变方案的条件 | T05 ADR；不要求每个普通实现细节都写 ADR |
| S4–S6 推演失败 | 对实际存在的并发、超时、依赖失败和数据冲突，定义系统结果与恢复方式 | T04/T05 契约、T07 验收用例 |
| S6–S7 验证风险 | 优先完成能验证关键不确定性的试验或最小业务闭环，用结果修正设计 | T08 实施任务、T07 实际证据 |
| S8–S9 运行与变化 | 检查发布恢复；业务或规模变化时分析影响，再决定维持、调整或迁移 | T09 运行卡、T10 变更记录 |

长期积累的是可复用的决策依据、契约、验证场景和实际结果。复盘聚焦本项目的遗漏、返工与改进，工作方法通过连续项目逐步形成。

## 3. 按任务裁剪

| 路径 | 适用情形 | 最小成果 |
|---|---|---|
| 完整路径 | 新产品、重大模块、跨模块业务调整 | 各阶段适用成果；按当前迭代深入，不提前细化全部远期功能 |
| 功能路径 | 已有架构内增加或改变功能 | 变更需求、受影响的规则/契约/界面、实现任务、相关验收与交接 |
| 小变更路径 | 文案、低风险样式、明确局部修复 | 变更目的、范围、针对性验证、必要记录；不强制重写蓝图 |

影响权限、资金、个人数据、状态转换、共享接口、不可逆操作时，即使改动很少，也启用相应专项规则。不得仅用代码行数判断风险。标记“不适用”须写触发条件为何不存在，不必为不存在的能力新建系统。

### 裁剪后实际要做多少

规则库是按风险查询的目录，不要求每个小任务逐条填写全部规则。先记录本次适用规则、关键排除理由和完成条件；后续发现新风险再补充。

| 本次工作 | 最小记录与检查 | 不需要默认展开 |
|---|---|---|
| 已有页面低风险文案/样式调整 | T01 的目的/范围简记，T06 的既有基线与改动边界，实际渲染定向检查，结果与交接可合在一处 | 全套蓝图、ADR、MVP、自动截图测试平台 |
| 已有功能逻辑缺陷 | 相关需求/正确预期、改前复现、受影响调用方、修复及回归证据 | 无关页面改版、全站架构重写 |
| 新业务闭环或重要跨模块变更 | 适用 S0–S7；明确需求、结构、契约、体验、任务及验收；发布时启用 S8 | 尚未进入本轮的远期功能细节 |

复用已有记录和字段即可；T07/T12 的检查与结论可放在同一文件，不为每个模板新建文件。小变更仍遵守真实验证、既有授权和相关安全要求。

## 4. 成果状态与文档权威

成果须同时标明对象、阶段和状态。设计成果可按“草稿 → 待验证 → 设计已验收/可实施”流转；实现成果按“进行中 → 已实现待验收 → 实现已验收”流转。只交付设计时不必经过“已实现”。另可标记“阻塞”“已废弃”；发布状态另记 T09。每次状态变化记录执行成员、版本和证据；“有文件”不等于“已通过”。

T08 的任务状态说明工作进度，规则检查状态说明某条义务的检查结果，T12 的结论说明一个准确范围是否验收通过；三者不自动互相升级。简单项目可合并记录，仍需说明判定对象。

蓝图中的业务规则登记是业务规则的权威入口，可链接到模块规格，避免全部内容挤在一个文件。PRD 引用规则编号并拥有用户场景和功能验收条件；契约拥有精确的数据/接口结构；交互规格拥有界面行为；测试引用前述规格，不另创一套业务规则。每条信息只能有一个权威维护位置。

发现冲突：记录冲突 → 对照来源与已有决定，在授权范围内解决 → 同步受影响成果 → 重验受影响行为。缺少业务依据或超出权限时只暂停依赖工作，获取所需输入或授权。重要业务假设未经确认，不得被 AI 自动转成事实；已确认且未改变范围的事项不重复请示。

多任务项目同时按 [项目推进与多 agent 执行](07_项目推进与多agent执行.md) 安排增量、里程碑、依赖和当前任务。它不增加阶段，也不要求每个项目使用子 agent；任务完成仍须满足适用质量检查与验收。

移动 App 在 S0 启用 [08_移动App专项](08_移动App专项.md) 与 T13，并先判定模式：**模式 A（常规：既有 App 修改优化与契约对接）**——盘点原工程、继承视觉基线并直接消费 `contracts/` 通用契约包完成对接；**模式 B（条件调用：明确从 0 新建 App）**——启用新建流程，定平台/渠道/预算并评估 React Native + TS 或原生方案（S0–S2 定范围、S3–S4 定生命周期/同步/兼容、S5 做平台交互、S6–S7 按设备矩阵验收、S8–S9 管签名/提审/发布）。按实际能力选择 STD-MOB-01 至 STD-MOB-16；不要求每个 App 有离线编辑、推送或支付。

## 5. 阶段执行卡

工程质量与审计验收按 [质量基线](06_工程质量与审计验收基线.md) 执行：S4–S6 确定适用标准和可实施条件，S7 检查变更与整合结果，S8 分别记录发布准备和发布后结果。T12 维护验收矩阵、审计发现与例外；通过检查不自动扩大发布权限，不增加岗位分工或额外授课。

### S0 启动与现状盘点

- **本步目标：** 明确范围、现状、限制和下一项可执行工作。
- **输入：** 原始想法、已有项目材料、已有代码或系统、已确认决策。
- **操作：** 确定用户、平台、交付目标与排除项；明确已有授权和待获取输入；盘点现有能力与技术栈（已有项目先读取或运行 `node scripts/build-index-tree.mjs --write` 生成 `PROJECT_INDEX_TREE.md` 项目语义索引树，STD-GOV-05）；识别敏感数据、外部系统和上线范围；选择路径，固定本次工作流版本；修改型任务记录现有行为及相关检查基线，涉及界面时识别既有风格和用户允许改变的范围。
- **提问示例：** 我们是在新建软件还是修改已有系统？谁能决定业务规则？原有哪个功能可以复用？
- **成果：** T01 项目启动卡；`PROJECT_INDEX_TREE.md`（已有项目）或现有材料索引；适用规则清单初版。
- **完成条件：** 本次目标、范围和限制清楚；未知项已转为资料获取、技术试验或必要确认任务。
- **未通过：** 先补已有材料；涉及范围/权限的不明确事项只暂停相关工作。
- **规则：** STD-GOV-01 至 STD-GOV-05；修改行为启用 STD-QA-11，修改界面启用 STD-FE-05。

### S1 发现问题与验证价值

- **本步目标：** 形成有依据的问题定义及需要验证的假设（指令型需求确认业务决策边界）。
- **输入：** S0 启动卡、可访问且获授权的业务材料或团队负责人已确认的业务指令（DEC）。
- **操作：** 先区分**探索型需求**与**指令/契约型需求**：① 探索型需求访谈/观察代表性用户的真实任务，记录现有步骤、困难、频率和替代方法，区分用户原话、观察事实与团队推断；② 内部系统或负责人明确下达的指令型需求，直接登记已确认决策（DEC）、目标场景与不做边界，免除形式化外部用户访谈，直入 S2。比较改流程、复用已有软件和新开发；先验证最大不确定性。
- **提问示例：** 请讲最近一次发生的问题，而不是猜想未来会不会用。若为明确指令：本次核心业务验收边界和排除项是什么？
- **成果：** T02 问题与证据卡（指令型需求可合并在 T01/T03 登记 DEC 来源），必要的可行性试验记录。
- **完成条件：** 探索型有可追溯的问题依据、目标用户和价值假设；指令型有明确的负责人决策（DEC）与业务目标；证据不足时标记探索，不批准大规模实现。
- **未通过：** 探索型补研究或缩小场景；指令型向负责人澄清边界。AI 模拟访谈不能代替真实证据。
- **规则：** STD-REQ-01、STD-REQ-02、STD-AI-01。

### S2 范围、蓝图与需求规格

- **本步目标：** 确定本期范围，形成可验收的需求规格。
- **输入：** 问题证据、约束、已有能力。
- **操作：** 选择本次核心用户路径；明确做与不做；画系统边界和模块关系；给需求及规则编号；将每项 `REQ-xxx` 拆解为结构化、可独立测试的验收条件 `AC-xxx`（Given / When / Then），写清正常、异常、权限、数据条件；定义业务结果及质量指标。
- **成果：** T03 蓝图与需求规格（含结构化 `AC-xxx` 清单）、当前增量及按需定义的 MVP/里程碑，T07 验收场景初稿。
- **完成条件：** 每项本期需求有来源、优先级和明确 `AC-xxx` 验收条件；没有以“智能、高效、友好”代替定义；待定项不会被悄悄实现。
- **未通过：** 模糊需求拆成具体场景；证据不足退回 S1；超范围内容进入候选清单。
- **规则：** STD-REQ-01 至 STD-REQ-04、STD-QA-01、STD-FLOW-01。

### S3 业务对象、规则与状态

- **本步目标：** 形成业务对象、权限、状态和行为规则。
- **输入：** 蓝图、需求、现行业务规则。
- **操作：** 定义业务术语、对象关系、角色权限及数据范围；对有生命周期的对象写状态表；逐个动作检查前置条件、状态变化、输出、失败、重复与并发；区分事实数据和派生数据。
- **成果：** T04 对象/权限/状态/行为契约；更新规则登记。
- **完成条件：** 核心动作可从用户意图追踪到业务结果；没有无法处理的状态、权限漏洞或含糊失败结果。
- **未通过：** 对照业务依据解决矛盾，缺少事实则补充确认；复杂度过高时缩小流程。只给有状态变化的对象写状态机。
- **规则：** STD-BIZ-01 至 STD-BIZ-04、STD-DAT-01、STD-SEC-01。

### S4 架构、数据与接口设计

- **本步目标：** 确定系统结构与关键技术取舍，形成可执行契约。
- **输入：** 业务模型、已有实现、平台限制、性能与成本目标。
- **操作：** 新建项目通过 `node 规范文件/starter/init-project.mjs --target .` 一键初始化**团队黄金技术栈底座（STD-ARC-09）**（Web 前端：React 18/19 + TypeScript strict + Vite + Tailwind CSS + Preline UI〔含 `usePrelineInit` 路由挂载与 `src/styles/theme.css` 品牌 Token，或按需 Meta StyleX/Lexical 生态〕+ Zustand/TanStack Query；后端：Node.js LTS + Hono/Fastify + TypeScript + Zod + Pino 结构化日志；数据库：**统一采用 PostgreSQL 16 + Prisma ORM** 与预置 `User/Session/AuditLog/IdempotencyRecord` 底座表，严禁 SQLite；认证权限采用 [auth-rbac-baseline.md](contracts/auth-rbac-baseline.md) 可吊销会话与三层 RBAC 拦截 `STD-SEC-05`；若涉及文件上传、导出或异步/定时任务，遵循 [storage-jobs-baseline.md](contracts/storage-jobs-baseline.md) `STD-DAT-05`；移动端默认走既有 App 契约对接，若明确从 0 新建则按 STD-MOB-01 调用新建分支评估 React Native + TS 或原生），已有项目沿用既有技术栈，仅在黄金栈无法满足硬约束时写 ADR 申请偏离；直接继承 [contracts/](contracts/README.md) 同构通用契约包（前端只引 `base-contract.schema.ts`，服务端同步指纹引 `fingerprint.server.ts`）；记录契约与 Schema 初始 SHA-256 指纹；必要时做可复现的小试验。
- **成果：** T05 架构结构/黄金栈采用或偏离 ADR/通用契约与 RBAC 基线引用及工程质量配置；接口 Schema 或 OpenAPI（继承 `openapi-baseline.yaml`）；PostgreSQL `schema.prisma`；质量预算。

## 6. 每次阶段切换或恢复工作的最小检查

1. 当前有效版本、相关需求与来源是否可定位，已有决定及理由是否记录？
2. 业务结果、约束和异常是否清楚？
3. 哪些已确认、哪些是假设、哪些实际验证过？
4. 哪些条目阻塞下一步，你将怎样获取答案或解决？
5. 哪些独立工作可继续，具体下一步是什么？

所谓“完成”，是对应证据足以支持这个阶段的判断，不是文件篇幅、勾选数量或 AI 的结论。阶段通过不扩大原有操作权限。

## 7. 新手术语速查

| 术语 | 本工作流中的含义 |
|---|---|
| PRD | 产品需求规格：描述做什么、为何做、用户如何使用与怎样验收 |
| 蓝图 | 整体业务范围、模块关系、术语及业务规则的入口 |
| 契约 | 调用或协作双方事先明确的输入、输出、行为与失败约定 |
| Schema | 机器可检查的数据结构与约束描述 |
| 状态机 | 一个业务对象允许处于哪些状态、哪些操作可以改变状态 |
| 幂等 | 同一个操作重复到达时，不产生额外的业务效果 |
| ADR | 技术决策记录：问题、备选方案、选择理由和影响 |
| Reference | 外部依据、内部规格引用或代码调用关系，需区分语义 |
| Design Token | 颜色、间距等有名称的设计变量，便于设计与代码一致 |
| Custom Hook | React 中复用有状态交互或请求生命周期逻辑的 `use*` 函数 |
| ATDD 四步闭环 | 需求 `REQ` → 结构化验收条件 `AC` → 先行测试 `TEST(@req/@ac)` → 编码实现 `TASK` → 指纹回填关闭的强绑定链路 |
| SHA-256 指纹 | 对请求载荷、契约 Schema、锁文件或验收证据生成的防篡改与防过期数字摘要 |
| 回归验证 | 修改后检查既有重要行为仍然正确 |
| 可观察性 | 通过日志、指标等理解系统发生了什么，定位失败原因 |
