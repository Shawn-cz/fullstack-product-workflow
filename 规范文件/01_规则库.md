# 设计与工程规则库

版本：0.8.0｜112 条规则｜使用顺序：先判断触发条件，再执行与检查。编号不因重排改变。

所有适用规则由当前成员贯通执行，各分类表示项目工作内容，不划分岗位。本库是面向零开发经验全栈产品设计团队的建议基线；正式项目在 T01 记录采用版本和适用条目。表中动作对已启用的条目为必做要求。不适用需简述原因；例外需记录理由、影响、补偿措施、跟进安排和到期复核点。适用的权限边界、真实性要求以及已有授权限制不能因例外记录而被取消。

检查状态统一为：未开始、待验证、通过、不通过、不适用、已批准例外。完成阶段前不得把“待验证”写成“通过”。资料来源见 [05](05_来源与更新机制.md)；本库是团队综合规则，未逐条等同外部标准，不据此声称符合某项认证。

架构、代码和验收的具体执行方法见 [工程质量与审计验收基线](06_工程质量与审计验收基线.md)。规则编号与强制动作以本文件为准；06 提供应用说明和阶段检查方法。对正式标准仅采用明确选定且可核实的范围；组织/工具实践不等于普遍强制标准。

## D. 架构与技术决策

| 编号 | 触发条件 | 必须执行 | 证据/检查 | 未通过处理 |
|---|---|---|---|---|
| STD-ARC-01 | 新技术、重大结构或依赖选择 | 比较现有方案和成熟替代；记录收益、团队能力、维护/成本及退出条件 | T05 ADR；新依赖有官方来源、许可及维护状态 | 无必要收益不引入；未确认的许可限制先澄清 |
| STD-ARC-02 | 模块划分或跨模块调用 | 定义职责、依赖方向与对外入口；优先满足需求的简单结构 | 模块图/数据流，无未经定义的跨模块改库 | 调整边界；不默认微服务或事件总线 |
| STD-ARC-03 | 关键能力不确定 | 先写试验问题、样本、环境、成功条件再做技术试验 | 可复现试验记录，列明与真实场景差距 | 调整方案或缩小范围，不能以演示代替证明 |
| STD-ARC-04 | 有性能、容量、可靠性要求 | 定义设备/网络/数据量/并发、指标、目标和成本预算 | 质量预算及测量方法；前后端分别测量 | 缺目标不能宣称“高性能”；先建基线 |
| STD-ARC-05 | 新系统或重要结构变化 | 记录架构范围、需要解决的问题、静态结构、关键运行路径及部署关系；视图之间使用一致名称 | T05 与实际模块/接口对应；按需参考 C4，来源 SRC-17/18 | 图与实现不符先更新；不强制画全四层 |
| STD-ARC-06 | 划分模块或修改依赖 | 集中同一业务规则，封装内部状态，经明确入口交互；控制耦合，不新增无理由的循环依赖 | 模块依赖/导入检查及关键调用路径；参考 SRC-27 | 修正越界调用或记录有依据的结构例外，不机械增加抽象层 |
| STD-ARC-07 | 确定架构方案 | 将重要质量要求转成场景，比较可行方案的收益、损失与限制 | T03 质量场景、T05 ADR 及试验；SRC-16 为质量模型参考 | 未测量的判断标假设，不能凭技术名词判优 |
| STD-ARC-08 | 架构约定可能在迭代中失守 | 为关键边界和业务不变量选择可重复检查，变更时检查实际漂移 | 按项目选导入约束、契约校验、事务/权限场景；低成本人工检查也可 | 修复新增违反或明确迁移计划，不要求专门购买架构工具 |
| STD-ARC-09 | 新建项目或新模块技术选型 | 无既有仓库强约束时，默认继承团队黄金技术栈（Web 前端：Vue 3 + TypeScript + Vite + Tailwind CSS + Element Plus/Naive UI + Pinia；后端：Node.js + Hono/Fastify + TypeScript + Prisma + SQLite/PostgreSQL；移动端：uni-app Vue 3 或 Capacitor）；仅当黄金栈经证实无法满足硬约束时，通过 T05 ADR 申请偏离并由团队负责人批准 | T01/T05 记录采用黄金栈组合或已获批的偏离 ADR；依赖与目录符合黄金栈约定；参考 SRC-07/45/46 | 禁止成员或 AI 凭个人喜好在各项目随意更换语言、框架或 ORM；未获批偏离退回重选 |

## F. 接口与集成（参考 SRC-05、SRC-06）

| 编号 | 触发条件 | 必须执行 | 证据/检查 | 未通过处理 |
|---|---|---|---|---|
| STD-API-01 | 组件/模块/外部系统交换数据 | 约定输入、输出、可空性、错误和版本；HTTP 接口按需用 OpenAPI | T05 与实际请求/响应核对，Schema 校验 | 契约冲突先解，模拟数据不另造字段 |
| STD-API-02 | 接口对客户端开放 | 统一认证与业务授权、分页排序、错误码及可公开错误信息 | 成功、错误与越权响应；错误格式可参考 RFC 9457 | 不把业务失败伪装成功，不返回内部堆栈 |
| STD-API-03 | 网络调用、Webhook 或异步任务 | 定义超时、有限重试、可重试条件、去重、顺序及结果查询 | 模拟超时/重复/乱序；可写操作不可盲目重试 | 不确定结果先查状态；Webhook 验证来源并防重放 |
| STD-API-04 | 接口或字段变化 | 检查消费者与兼容性；明确迁移/弃用期限及契约版本 | 调用方清单、兼容验证、变更说明 | 破坏性变化不静默上线 |
| STD-API-05 | 使用 HTTP API | 按方法/状态码语义设计；读取操作不承载用户请求的业务写入；认证相关缓存与重试按实际语义处理 | 对照 RFC 9110（SRC-23）、接口契约与负向用例 | 不把 HTTP 方法名称当作业务去重保证；修复语义冲突 |
| STD-API-06 | Schema、类型、客户端或模拟数据有多份表达 | 明确契约权威源及派生方向；适用时生成类型/客户端/样例并记录命令和工具版本；检查真实生产方/消费方及模拟数据与契约一致 | T05 权威/派生表、校验或生成差异；含错误、空值和边界；无法生成可用明确人工比对 | 不直接改生成文件后遗留源差异；不能只验证客户端和由同一错误契约生成的模拟接口 |

## P. 填写规则检查记录

实际项目保存：规则编号｜适用原因｜执行成员｜状态｜对应版本｜证据路径｜问题与下一步。来源失效、检查未运行、尚未获得输入应分别记录，不统一写“通过”。例外由当前执行成员在已有权限内处理并记录理由；重大业务变化缺少依据或超出授权时获取确认，普通可逆实现细节自主判断。执行成员字段用于追溯，不构成阶段岗位分工。

## Q. 如何把“质量好”变成可测量的条件

下面提供可采用的起点，避免新手只填写“快速、易用、安全”。引用指标只是质量的一部分，实际项目须在 T03 选定适用范围和预算。

| 质量维度 | 具体写法或参考值 | 怎样验证及限制 |
|---|---|---|
| Web 加载/交互/稳定性 | Web Vitals 的良好体验参考：LCP ≤ 2.5 秒、INP ≤ 200 毫秒、CLS ≤ 0.1 | 按移动/桌面区分，考察页面访问的第 75 百分位；实验室单次测试不能代替真实用户分布。依据 [SRC-12](https://web.dev/articles/vitals) |
| 可访问性 | Web 项目建议选择 WCAG 2.2 AA 作为目标；映射适用成功标准并列出人工与自动检查 | 键盘完整操作、焦点可见、表单标签/错误关联、放大/重排等需实际验证；本清单不是完整符合性证明。依据 [SRC-03](https://www.w3.org/TR/WCAG22/) |
| 用户任务 | 写“目标角色在给定材料下完成提交并能找到结果”，记录是否需要帮助和在哪里失败 | 代表性任务观察；样本少时用于发现问题，不夸大为总体成功率 |
| 接口性能 | 写“指定端点、指定并发和数据规模、p95 延迟目标、错误率及测量窗口” | 预算由实际业务决定；不能拿空数据库结果代表生产规模 |
| 业务正确性 | 写“同一提交意图并发重试只产生一次业务效果；无权用户无法读取他人数据” | 同时检查响应、持久化记录和外部副作用，不能只看按钮状态 |
| 恢复能力 | 写清允许的数据损失窗口和恢复时间目标 | 做恢复演练并核对数据；有备份文件不等于能恢复 |
| AI 质量 | 按任务定义正确/错误、错误成本、拒绝/接管条件、延迟与费用预算 | 使用代表性留出样本和人工抽查；单一平均准确率不能覆盖越权或高损失错误 |

| STD-AUD-05 | 采用抽样审计 | 定义总体、风险分层、样本选择和未覆盖范围；关键验收场景逐项验证 | 样本清单与选择依据；发现问题扩大相关范围 | 不用少量成功样本推出全量通过；未验证边界明确保留 |
| STD-AUD-06 | 交付或归档验收结果 | 保留结论对应的版本、证据索引、缺陷/例外与决定依据；变更后重新判断影响 | T12 验收记录与 T10 交接，可恢复原判断 | 旧版本通过不得自动沿用到受影响的新版本 |
