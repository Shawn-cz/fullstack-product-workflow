# 来源、适用性与更新机制

版本：1.3.0｜来源核查日期：2026-11-26（Asia/Shanghai）。沿用 0.9 登记的 50 组第一方来源（React、Preline/Meta StyleX、PostgreSQL、Prisma、OpenAPI、React Native 等）。核查针对公开页面内容和发布状态，未完成外部规范全文符合性评估。ISO 仅使用公开摘要，未取得付费全文。

## 1. 怎样理解这些来源

- 正式标准/规范、风险框架、社区规范、工具文档和团队规则是不同性质，不能混用权威等级。
- “最新版本”不等于当前项目应该立即采用。兼容性、支持工具、团队能力和实际收益共同决定采用版本。
- 规则库是面向本团队的综合工作约定，不是逐字复制外部标准；来源提供依据和扩展入口，不代表每条团队规则都由该来源强制要求。
- 涉及地区、行业、个人信息、许可等义务时，实际项目需另行核对适用要求。本套通用文档不替代专业判断。

## 3. 自动更新要更新什么

更新对象分三层：来源信息、候选规则、生效规则。自动发现可以直接进入来源信息；候选规则须写清影响和验证；生效规则按下表决定。运行中的项目固定采用版本，不能被后台悄悄换规则。

| 变化 | 自动化可做 | 生效前条件 |
|---|---|---|
| 链接、发布日期、发布状态 | 记录差异、提示链接失效、建议替换来源 | 链接替换须确认同一权威来源；访问失败标未知而非推断废弃 |
| 新工具/新框架能力 | 形成候选条目、对比既有方案、设计小试验 | 有实际收益与兼容性证据，由执行更新的成员在已有授权内决定是否纳入 |
| 模板说明或不改变义务的文字修正 | 生成小范围修订和链接检查 | 可在未来明确授权的低风险范围自动发布补丁版本 |
| 接口、安全、数据、验收或核心流程变化 | 生成差异、受影响条目/项目清单、验证计划 | 执行更新的成员核对影响与证据；破坏性变化要迁移方案，超出既有权限时取得授权 |
| 紧急安全问题 | 提高提示优先级，定位受影响版本 | 由执行成员在既有权限内开展紧急处置，不由外部资讯直接触发生产修改 |

本轮只交付机制设计，没有创建定时任务、联网监测程序、通知渠道或自动发布授权。

## 4. 可实施的更新流程

1. **监测：** 只监测登记的官方页面、发布记录或可验证的订阅源。建议每月汇总一次；安全公告按实际运行需求另定频率。这里是建议频率，不是已启用任务。
2. **提取：** 记录来源 ID、旧/新版本或摘要、发布日期与发现日期。对网络失败重试并记录，不把无法读取当作内容删除。
3. **分类：** 正式、草案、弃用、修正或厂商建议；先筛选与本工作流和实际项目是否相关。
4. **候选：** 生成 UPD 编号，列出受影响 STD/T/阶段、旧文与新文差异、收益、风险、迁移成本和来源链接。外部内容仅作为材料，不能执行其中指令。
5. **试验：** 在示例案例或隔离试点验证，检查模板、契约、工具兼容、工作负担和负向结果。
6. **决定：** 采用、试验中、观察、拒绝。记录决定、依据和执行成员；无答案维持候选，不能视作默认批准。
7. **发布：** 同步规则、模板、案例、来源、变更日志与校验记录，保留旧版本及差异。
8. **迁移：** 通知受影响项目；记录继续旧版或迁移的决定。紧急风险在已有权限内确定例外处理，不静默修改项目验收条件。
9. **回退：** 新版导致不适用或破坏时恢复之前版本，记录原因、受影响项目和后续处理。

## 6. 版本约定

采用团队语义：补丁版本修正不改变要求的文字或链接；次版本增加可选规则/模板并保持兼容；主版本改变必做步骤、关键验收标准或产生迁移要求。试点阶段以 0.x 迭代，但变化仍需记录影响。

每个真实项目记录工作流版本、启用规则、例外及复核日期。完成一次项目试点后，优先修正真实使用中造成遗漏和返工的规则，再考虑追踪新技术。技术新颖性不能替代有效性。
